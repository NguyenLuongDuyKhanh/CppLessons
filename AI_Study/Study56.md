Great question. There are actually **three different layers** involved:

1. **Your C++ source code**
2. **The compiled assembly generated by the compiler**
3. **The actual Linux system call** executed by the kernel

A `pthread_create()` call is a good example because what looks like one function call in C++ eventually results in a `clone()`/`clone3()` system call.

---

# Example C++ program

```cpp
#include <pthread.h>
#include <iostream>

void* worker(void*)
{
    std::cout << "Hello\n";
    return nullptr;
}

int main()
{
    pthread_t tid;

    pthread_create(&tid, nullptr, worker, nullptr);

    pthread_join(tid, nullptr);

    return 0;
}
```

Compile without optimization to make assembly easier to read:

```bash
g++ -O0 -S main.cpp
```

---

# The generated assembly

The exact output depends on the compiler version, but it looks roughly like this (x86-64):

```asm
main:
    push    rbp
    mov     rbp, rsp
    sub     rsp, 16

    lea     rax, [rbp-8]        ; &tid
    mov     ecx, 0              ; arg
    lea     rdx, worker         ; start routine
    mov     esi, 0              ; attr
    mov     rdi, rax            ; pthread_t*

    call    pthread_create@PLT

    lea     rdi, [rbp-8]
    mov     rdi, [rdi]
    mov     esi, 0

    call    pthread_join@PLT

    mov     eax,0
    leave
    ret
```

Notice something important:

There is **no system call instruction (`syscall`) here.**

The compiler simply generates a normal function call:

```asm
call pthread_create@PLT
```

The PLT (Procedure Linkage Table) is used for dynamic linking.

---

# Inside `pthread_create`

`pthread_create()` is implemented in the C library (typically glibc).

Internally it:

* allocates a stack
* sets up thread-local storage
* prepares thread metadata
* eventually performs

```text
clone(...)
```

or on newer Linux

```text
clone3(...)
```

which is the actual kernel system call.

---

# Assembly for a system call

Linux x86-64 system calls use

```asm
syscall
```

Suppose we want

```cpp
write(1, "Hello", 5);
```

The compiler might emit

```asm
mov     eax, 1          ; SYS_write
mov     edi, 1          ; fd
mov     rsi, msg        ; buffer
mov     edx, 5          ; length
syscall
```

The `syscall` instruction switches from user mode to kernel mode.

---

# pthread_create eventually becomes clone

Internally, glibc eventually executes something similar to

```asm
mov     eax, SYS_clone
mov     rdi, flags
mov     rsi, child_stack
mov     rdx, ptid
mov     r10, tls
mov     r8, ctid
syscall
```

This tells Linux to create a new thread.

---

# Can we create a thread using assembly directly?

Yes.

Instead of calling `pthread_create`, we can invoke the `clone` system call ourselves.

This is essentially what glibc does (although the real implementation is much more complex).

Example:

```asm
mov     rax, 56          ; SYS_clone
mov     rdi, flags
mov     rsi, child_stack
mov     rdx, ptid
mov     r10, tls
mov     r8, ctid
syscall
```

If successful,

* parent receives child's TID
* child receives 0

After the syscall returns, the child begins execution using the stack supplied.

However, this **does not** create a POSIX thread by itself. `pthread_create()` also initializes thread-local storage, signal handling, cleanup handlers, cancellation state, and integrates with the C runtime. Calling `clone()` directly is lower level and requires you to set up much of that yourself if you want pthread-compatible behavior.

---

# Inline assembly example

Here's a minimal example of making the `clone` system call from C++ using inline assembly:

```cpp
long ret;

asm volatile (
    "mov $56, %%rax\n"     // SYS_clone
    "syscall"
    : "=a"(ret)
    :
    : "rcx", "r11", "memory"
);
```

This only issues the syscall. It is **not enough** to create a usable thread because the required arguments (flags, stack, TLS, etc.) are missing.

---

# The complete picture

```
C++ source

pthread_create(...)
        │
        ▼
Compiler

call pthread_create@PLT
        │
        ▼
glibc

allocate stack
setup TLS
prepare TCB
        │
        ▼
clone() wrapper
        │
        ▼
syscall instruction
        │
        ▼
Linux kernel

create task_struct
create scheduling entity
return to parent
start child
```

This layered design is why most C++ code never contains a `syscall` instruction directly: the compiler generates ordinary function calls, the C library handles runtime setup, and only the library (or your own low-level code) executes the architecture-specific `syscall` instruction to enter the kernel.
